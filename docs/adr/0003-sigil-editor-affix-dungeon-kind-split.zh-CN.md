# 为全局词缀黑名单区分钥匙编辑器中的词缀与地下城类型（#502）

[English](0003-sigil-editor-affix-dungeon-kind-split.md)

钥匙 Profile 编辑器原本以地下城为中心：每行都显示“地下城”选择器和条件列表，用户无法
表达“在所有钥匙上把该词缀列入黑名单”这种不指定地下城的全局规则。过滤器已经支持这类
规则（`_match_affixes_sigils` 会在钥匙包含指定词缀时匹配），但编辑器既不能创建也不能
加载，并会对顶层词缀名抛出 `KeyError`。

## 决策

编辑器把每条钥匙规则分类为 `affix` 或 `dungeon`，并按类型渲染。`kind` 根据名称推导，
不写入 Profile：

- 名称存在于 `sigils.json` 的地下城映射时，`derive_sigil_kind(name)` 返回 `dungeon`，否则返回 `affix`。
- `sigil_name_dict_for_kind(kind)` 按类型选择名称池：词缀使用次要、主要和正面词缀，地下城使用地下城列表。
- **词缀类型**行表示该词缀的全局黑名单或白名单，只显示“词缀”选择器。条件列表及其增删按钮会隐藏，因为条件属于指定地下城。
- **地下城类型**行保留现有“地下城”选择器和条件列表。
- `CreateSigil` 提供地下城/词缀类型下拉框，并据此重新填充名称池。

名称验证保持宽松：`SigilConditionModel.name_must_exist` 只检查名称是否在词缀与地下城的
合并字典中，不强制对应具体类型。

## 影响

- 不改变 Schema，也不需要迁移；仍通过现有 `SigilConditionModel` 的 `{name, condition}` 往返保存。
- 同时存在于两个名称池的名称会被视为 `dungeon`。当前数据没有重名，因此接受这一规则。
- 宽松验证不会在加载时拒绝错误分类的名称；这是为了避免向后兼容风险。
- 此修复是钥匙稀有度 GUI 控件（ADR-0002）的前置条件。
