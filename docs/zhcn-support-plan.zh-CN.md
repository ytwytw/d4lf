# 简体中文支持计划

**简体中文** | [English](zhcn-support-plan.md)

本文档记录为 Diablo IV 添加 `zhCN` 支持的工程与安全决策。它是一份工作计划，并不声称本工具已获得暴雪授权，也不声称账号不可能被处置。

## 为什么早期的多语言尝试困难重重

完整的 Git 历史中有一个未合并的日语分支提交 `4c22e4b`（`Add Japanese (jaJP) language support`）。它增加了 3,000
多行代码，大部分是生成的语言文件，但一直停留在陈旧的
`fute/main` 引用上，没有跟进后来的赛季解析器变更。

有用的教训并不是说 CJK 文本不可能实现。UTF-8 本就能到达 Python。困难的部分在于：

- 物品框定仍然假定大写拉丁字母物品名和英文鼠标/动作按钮终止符。日语分支添加了一个
  `Item Power` 位置特例，而不是可复用的本地化语法。
- 解析器规则将英文字面量与不断增多的语言专属 tooltip 查找混在一起。每个赛季都会多出一个分支可能漂移的地方。
- 语言文件以一个大型快照交付，没有源构建锁定、源哈希、覆盖率报告或自动过期数据检查。
- 日语变更没有随之添加解析器回归测试。因此当本地化代码改变共享行为时，主英文解析器没有任何保护。
- 一些生成的值仍是英文占位符，例如 `custom type material` 和 `custom type sigil`。缺失的翻译可能静默地变成运行时行为。
- 运行时显示文本与 Profile 键耦合过紧。修改一个本地化值可能改动
  `ItemType` 枚举，或破坏用户已有的英文键 Profile。

## 架构

实现将四个关注点分离：

1. **规范化应用 ID。** 现有 `enUS` Profile 键保持为稳定 ID。本地化名称只是用于解析和显示的别名。加载其他本地化绝不会改动枚举值。
1. **本地化语法。** `grammar.json` 负责稀有度标签、物品边界、tooltip 锚点和特殊物品
   标识符。解析器调用语法操作，而不是堆积 CJK 专属分支。
1. **版本化数据适配器。** Companion、d4data 和注明署名的 D2Core 输入以显式 UTF-8
   读取，按源身份连接、哈希，并附带机器可读的质量报告。有歧义的别名会被拒绝，而不是采用首次匹配行为。
1. **失败即关闭的发布门禁。** 当一个本地化的源构建过期、稳定 ID
   缺失或新增、源哈希变化、别名有歧义或必需翻译是占位符时，它就不具备自动化就绪条件。

AI 工具可以加速映射、测试生成和审查，但生成的文本绝不会绕过这些门禁。
对于可能标记、移动、使用或丢弃物品的动作，AI 的猜测不是充分的证据。

### 统一语言切换

`general.language` 是应用本地化与游戏解析的唯一事实来源。设置窗口在 **System & Paths** 下提供
`English (enUS)` 和 `Simplified Chinese (zhCN)`。更改它会：

- 重建并重新翻译已打开的 D4LF 窗口；
- 在正在运行的脚本处理器中重新加载匹配的 `assets/lang/<locale>` 解析器数据；
- 更新诊断捕获的语言区域；并
- 应用本地化安全策略，包括在重新加载本地化资产之前停止任何活动中的交互。

显示标签绝不会被持久化为配置值。控件保留稳定 ID，例如 `zhCN`、
`dark` 和 `blacklist`，因此翻译 UI 不可能改动 Profile 或解析器配置。该切换不会修改
Diablo IV 自身的语言设置；用户必须将游戏客户端配置为相同的语言区域。

## 数据来源

完整的 [Diablo4Companion 仓库](https://github.com/josdemmers/Diablo4Companion) 提供具有共享
SNO/内部名身份的配对 `enUS` 与
`zhCN` 游戏记录，并采用 MIT 许可证。d4data 提供现有的上游构建出处。其 README 指出直接的游戏资产仍属暴雪财产。

当配对的游戏数据没有翻译时，D2Core 补充词缀、威能、暗金和护符装备（Talisman）。
它不是目录成员资格的事实来源，从 D2Core 快照中缺席绝不会禁用已有的中文
别名。项目所有者已确认可以直接使用并公开再分发，但需在 README 中署名；
`docs/third-party-data.md` 与公开导出门禁保留了这一要求。原始快照不会被提交：一个有界适配器只下载八个公开的静态
JSON 文件，验证配对的 `(key, id)` 身份集合，锁定其 URL 和 SHA-256 哈希，并输出逐记录的翻译出处。它绝不绕过交互式规划器。

D2Core 和当前的 d4data 将 `shade_damage` 与 `shadow_damage` 识别为不同的词缀，尽管两者的官方简体中文文本都是
`暗影伤害`；`poison_damage` 与 `poisoning_damage` 同为
`毒素伤害` 的情况也一样。tooltip 模板保留了一个区分信号：一种形式使用小数范围边界，另一种使用整数边界。`grammar.json`
记录了这些狭窄的规则。官方的 `malicious` 与 `virulent` 威能名称都是
`恶毒`；它们被声明为一个显式的等价规范化 ID 组，因此任一导入的 ID 都匹配同一个可见的游戏名称，而不需要编造翻译。

当前赛季的范围和源评估记录在 `docs/zhcn-scope-audit.md` 中。核心装备、护符装备和
D4LF 可选的符印/贡品筛选器是独立的交付层级。历史非装备解析器类型不会阻塞装备就绪。

已提交的源快照记录：

- 当前 Companion 检出是提交 `6e52cac`（`Updated data for v3.1.1.72903`），但在其 zhCN 文件上次为
  `3.1.0.72592` 刷新之后，只有受控的 `Aspects.enUS.json` 发生了变化。
- 本地 d4data 检出在提交 `5b68e74` 处标识构建 `3.1.1.72836`。
- D2Core 静态数据库标识构建 `72698`。
- 本地语法验证参考标识客户端构建 `3.1.0.72810`。

[暴雪当前的补丁说明](https://news.blizzard.com/en-us/article/24287406/diablo-iv-patch-notes)
将全平台在线客户端标识为 `3.1.1.72836`，与 d4data
一致。这些构建差异必须保持可见。把 `72836` 数据重新标注为 `72592`、`72698`、`72810` 或
Companion 仓库级的 `72903` 都是无效的；真实的客户端捕获可以验证观察到的语法和别名，但它不能证明完整的赛季数据覆盖。

源清单包含全部 2,742 个运行时稳定键，无论 D2Core 覆盖如何。它解决了 2,724 条记录：
2 条装备记录和 16 条 D4LF 扩展记录仍未翻译。`excluded_historical_records` 为零，因此所有现有的非空中文别名都参与运行时解析。

清单仍然包含 `"runtime_ready": false`，这是完整多语言目录发布门禁的要求。受防护的交互已为单独验证的装备范围启用。完整目录的晋升仍被以下因素阻塞：`72698`/`72810`/`72836`/`72903`
混合的源与验证构建，以及 18 条未翻译记录；当前已不存在提供者分歧。已知的重复中文别名已被显式消歧或分组，不再导致
`source_quality_ok` 失败。这些是独立的、机器可读的发现，而不是一个不透明的覆盖率百分比。

提供者冲突是失败即关闭的。它们在本地化清单和质量报告中都可见，并阻止
`runtime_ready=true`，直到记录一个明确的经审查解决方案；仅凭提供者可用性或优先级并不是发布批准。

五个历史非装备物品类型（`Elixir`、`Incense`、`Material`、`TemperManual` 和 `Tome`）被明确
报告为从装备里程碑中排除。`Nightmare Sigil` 已从公开的配对
`Type=sigil` 身份解析，不再需要仅为发现其物品类型标签而进行客户端捕获。

## 赛季更新流程

对于每个补丁或赛季：

1. 获取两个上游仓库并记录精确的提交。
1. 获取并验证有界 D2Core 快照；强制语言区域配对和记录下限，然后锁定其
   发现的构建、URL、哈希和派生的翻译记录索引。
1. 从显式的数据更新提交读取游戏数据构建，而不是 Companion 应用版本。
1. 将源清单、哈希、本地化数据包和质量报告生成到一个临时目录。
1. 将稳定 ID 集合和源哈希与已提交的锁定进行比较。对新增、删除、改名的
   源文本、缺失的中文记录、占位符和别名冲突进行分类。
1. 如果提供者构建不一致或任何必需记录未解决，则阻止晋升。
1. 离线重放已检入的合成夹具和本地原始 TTS 捕获；绝不将原始捕获加入 Git。
1. 在替换已提交的数据包之前，运行完整的英文和本地化测试套件、lint 检查和发布打包。

这一流程在发布决定之前都可以无人值守。新的歧义术语、源许可证变更、新的
TTS 布局或构建不匹配都刻意要求人工审查。

## 账号风险

暴雪当前的
[EULA](https://www.blizzard.com/en-us/legal/fba4d00f-c7e4-4883-b8b9-1b4500a402ea/blizzard-end-user-license-agreement)
和[反作弊协议](https://www.blizzard.com/en-us/legal/cd5930c0-2784-420c-a23d-1e0d6ff8599b/anti-cheating-agreement)
对未经授权的第三方程序、自动化和便利游戏玩法的软件保留广泛的自由裁量权。平台可能检测并举报未经授权的程序，账号处置可能包括暂停或封停。D4LF
自身也记录说明它会读取无障碍 TTS，并在其正常英文模式下发送鼠标和键盘输入。

因此不存在可辩护的数字封禁概率，开源代码或只读模式都不意味着暴雪已授权该软件。本分支使用的风险排序是：

- **最高：** 在连接游戏时自动标记、点击、移动、使用或丢弃物品。
- **仍然重大：** 在游戏进程环境中运行基于 DLL 的第三方监听器，即使消费方只读取文本。
- **暴露较低，但不为零：** 在游戏关闭后进行离线生成和重放。

正常的 `zhCN` 战利品筛选交互受到与 `enUS` 相同的运行时检查防护：诊断捕获会阻止
输入，每次交互都要求 Diablo IV 保持前台窗口，更改语言区域或启动诊断捕获会停止活动中的交互。捕获工具只拥有现有的命名管道，并记录由
`saapi64.dll` 发出的消息；它不启动游戏、不检查游戏内存、不注入新代码、不移动指针、不按键，也不做物品决策。这减少了行为和爆炸半径，但并不是免于检测或账号处置的承诺。

候选构建使用独立的 `zhcn` 预发布版本，并保持自动更新禁用。只有在
`ytwytw/d4lf` 拥有稳定的本地化发布和更新源之后，才重新启用自动更新；否则更新可能会用不兼容的构建替换已安装的候选。

## 客户端证据状态

针对客户端构建 `3.1.0.72810` 的本地捕获已离线审查，并保留在 Git 之外。两个诊断
会话包含 4,224 条原始 TTS 记录和 116 个完整物品框。当前解析器接受了全部 116
个框，覆盖 12 种装备类型中的普通、魔法、稀有、传奇、暗金和神话装备，以及
三个符印框。七十个非暗金装备框还同时通过了生成的保留筛选器和生成的
拒绝筛选器。这些轨迹包含 30 个收藏物品前缀和 22 个空插槽标签。

七个自动视觉失败包已从它们的完整截图重放。在修正负 ROI
裁剪和左侧面板 tooltip 位移之后，每张截图都产生了有效的 tooltip 裁剪和位置感知
解析。这些截图和原始记录不是发布夹具，因为它们可能包含可识别账号的
像素和文本。

其余的人工证据刻意保持较小规模：

- 一次针对背包、已装备和商人布局的打包应用冒烟通过。现有捕获主要
  来自储物箱，不能端到端证明这三种放置位置。
- 一条标记为垃圾的物品轨迹。收藏和已镶嵌物品已有代表，但没有捕获到的物品名前缀
  能标识一件已经是垃圾的物品。
- 只有在需要这些交付层级时，才为护符装备（护身符和印记）以及 D4LF 的非装备
  符印/贡品筛选器进行单独的可选捕获。
- 在交互已处于待处理状态时进行一次手动诊断捕获转换检查。

收集到的轨迹离线重放。它们不会自动成为源翻译，且不得记录个人或可识别账号的元数据。

## D2Core 构建导入

Profile 导入器接受来自 [D2Core 网站](https://www.d2core.com/)的公开规划器链接。历史测试使用了分享码
`20eK`；它的旧规划器 URL 目前返回 `404`，因此只保留为回归测试 fixture，不再作为文档中的有效链接。
导入器通过 D2Core 页面已加载的 SDK 读取公开构建，并针对 D2Core 当前的 `enUS` 静态目录解析装备。
英语仅用作通往 D4LF 稳定 ID 的语言中立桥梁，因此生成的 Profile 在 `enUS` 或 `zhCN`
游戏语言设置下都能工作。

所有非空装备变体都会被导入。支持的字段包括装备类型、普通词缀和强力词缀、暗金、传奇威能升级和转化威能升级。回火词缀被刻意
排除，与其他构建导入器保持一致。D2Core 巅峰、技能、雇佣兵、消耗品和攻略正文
不在此装备导入范围内。没有精确 D4LF 稳定 ID 匹配的新目录条目会被跳过并给出警告，而不是被猜测。
